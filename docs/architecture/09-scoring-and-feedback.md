# 打分与反馈闭环

打分系统最容易犯的错是**过早精细化**：定九项权重、算出「67 分」，但没人能解释这个数字，也没有数据支持那些权重。

Phase 1 的策略是：**硬门槛先行，打分从简，把回测所需的输入全部留档。**

---

## 一、硬门槛（不通过直接丢弃）

门槛是布尔判断，不参与打分。不满足就不该进入触达队列，浪费成本。

```text
1. 能否接触        有可达性已验证的联系人，且未命中抑制名单
2. 证据等级达标     至少 public_company_event（纯 agent_industry_inference 不够）
3. 预计订单额过底线  低于 Playbook 设定的最小交易额直接丢
4. 非禁售类别       未命中 Playbook 排除类别
5. 未重复           同一企业不存在活跃机会（Lead Ownership Lock）
```

门槛的价值在于**便宜**：全是内存或单表查询，先把大部分噪音挡掉，再对剩下的做贵的判断。

---

## 二、Phase 1 打分：三因子

过了门槛的候选按三个因子排序，**不做加权求和成百分制**：

| 因子 | 取值 | 来源 |
|---|---|---|
| 需求证据强度 | 七档离散值 | 代码依据证据等级推导（硬边界 3） |
| 预计订单价值 | 金额区间档 | 数量 × 参考单价，Decimal 计算 |
| 供应可获得性 | 高 / 中 / 低 | 匹配梯子能走到第几级 |

排序规则：先按证据强度分组，组内按订单价值排，同档再看供应可获得性。**这是字典序排序，不是加权平均**——它可解释，且不会出现「弱证据 + 大金额」压过「强证据 + 中金额」的荒谬结果。

### 为什么不用设计稿里的九项权重

`20% 需求真实性 + 15% 紧迫性 + 15% 订单价值 + …` 这套权重现在没有任何数据支撑，纯属猜测。九因子还很难 debug——有人问「为什么这个是 67 分」时，没人答得上来。

九因子的正确引入时机是：有了足够成交数据，能回测出哪些因子真正预测成交。所以现在要做的是**把回测所需的数据留下来**（下一节），而不是先编一套权重。

---

## 三、打分输入快照

**每次打分都要存下当时的输入。** 这是 Phase 2 能否做出真实权重的唯一前提。

```yaml
score_snapshot:
  opportunity_id: opp_123
  scored_at: 2026-08-07T...
  scorer_version: v1
  gates_passed: [reachable, evidence_ok, value_ok, category_ok, no_duplicate]
  factors:
    evidence_level: public_company_event
    estimated_order_value: {amount: 4500, currency: USD, basis: indicative}
    supply_availability: medium
  rank_bucket: B
  # 后续由结果回填
  outcome: null                # won | lost | null
  loss_reason: null
```

关键点：

- **快照不可变。** 后续打分产生新快照，不覆盖旧的。
- 记录 `scorer_version`，换算法后能分开评估。
- `outcome` 与 `loss_reason` 在机会终结时回填——这就是训练/回测数据。

**没有快照，Phase 2 的权重回测只能重跑历史数据，而历史输入往往已经不可复现。**

---

## 四、Loss Reason 闭环

Loss Reason 枚举见 [01-domain-model.md](01-domain-model.md#五loss-reason)。这里说它怎么用。

每条 lost 机会记录：死在哪个状态、当时的证据等级、已消耗成本、Loss Reason。据此可以回答：

```text
哪一类需求假设最容易被证伪？          哪些国家联系不上的比例特别高？
哪些品类总是找不到供应？              价格谈不下来集中在哪些产品？
哪个证据等级的转化率其实不如预期？
```

**这些答案直接改进下一轮探索策略。** 没有结构化归因，「根据结果改进」只能靠感觉。

---

## 五、必须监控的指标

不做泛化的电商经营大屏，但自主获客必须看这些：

```text
发现的需求信号数          生成的需求假设数
获得回复的客户数          已验证需求数
合格商机数                找到供应方案的需求数
等待真人处理的商机数       需求到寻源平均时间
寻源到报价平均时间         每个已验证需求消耗的成本
每个合格商机消耗的成本     退信率 / 退订率 / 投诉率
员工承诺按时完成率
```

**北极星指标**：每消耗一单位成本，产生了多少真实需求和合格商机。

不要优化：搜索次数、发现的公司数量、发送邮件数量、Agent 对话次数。这些都是活动量，不是产出。

---

## 六、人工接管 SLA

Agent 找到高意向客户后，如果员工一天不处理，前面的自动化全部白费。

Phase 1 监控两个指标：

```text
handoff_queue_depth        待接管队列深度
handoff_wait_time_p50/p95  从通知到有人接受的时长
```

这两个数本身就有用——老板要看的就是「哪些高意向客户在排队没人管」。

超时要升级：通知后一定时间无人接受，自动通知经理；再超时通知老板。

---

## 七、Phase 2 的三个挂载点

以下机制**现在不建**，因为 Phase 1 缺少它们工作所需的前提。这里记录挂载点，避免以后改动扩散。

### 1. 探索配比自适应分配器

设计稿建议「70% 需求优先探索 / 30% 现有能力辅助」。问题是冷启动时没有反馈数据，需求优先探索产出的假设证据等级低、转化差，而围绕现有供应能力找客户至少供应是确定的。一开始把 70% 投在低置信假设上会先烧掉大量预算。

**Phase 1**：做成老板可调的配置项，初期建议**反过来**（现有能力为主），并记全「每单位成本产出的已验证需求数」按策略分组的数据。

**Phase 2**：以该指标为反馈信号自动调配，本质是多臂老虎机。老板仍可手动倾斜。

挂载点：`domains/directives/` 的探索配比字段 + 上述指标的分策略记录。

### 2. 接管队列反压

待接管队列积压严重时，继续花钱找新客户是在毁灭价值——应该把预算挪到已验证需求的寻源和报价上。

但反压要压的是**成本配额**，而配额系统在 Phase 3。Phase 1 没有可压的对象，机制会空挂。

**Phase 1**：只做队列深度与等待时长两个指标 + 超时升级。
**Phase 2**：接入配额后加自动降配额。

挂载点：`HandoffQueueBacklogged` 事件（已在 `shared/events/catalog.py` 定义）。

### 3. 需求簇驱动寻源排序

需求聚类是整份设计商业价值最高的机制：八个客户都要不锈钢船用铰链，价值远大于八条独立商机——一次寻源服务多个买家、有谈价筹码、摊薄 MOQ 风险、还能沉淀成正式产品。

但 Phase 1 寻源是人工的，且已验证需求只有个位数，聚不出东西。

**Phase 1**：建 NeedCluster 模型与归簇逻辑（就是个表，很便宜）。
**Phase 2**：寻源队列默认按簇排序而非按单条需求排序；簇达到一定规模自动提议进入正式产品目录。

挂载点：`domains/demand/` 的 NeedCluster + `domains/sourcing/` 的队列排序接口。

---

## 八、给实现者的提醒

1. **不要提前引入加权求和。** 字典序排序够用，且能解释。
2. **打分快照是 Phase 2 的地基**，不要省。
3. 打分函数应是纯函数、无 IO、可单测，输入是候选加证据，输出是档位加排序键加解释文本。
4. 每个分数都要能生成人类可读的解释，说明为什么排在这个位置。
