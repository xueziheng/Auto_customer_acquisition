# ADR 0093：企业客户待分配池与当前负责人

- 日期：2026-10-14
- 状态：已接受，用户明确授权的新权限模型
- 前置：ADR 0091、0092

## 问题与决定

用户已确认「平台管理来源，企业管理员搜索并分配，员工跟进自己获分配的客户」。
此前搜索/后台补充立即把客户归给请求员工，manager 可查看下属，不符合新的企业工作方式。

新增交付保留公司取得事实并消耗原交付额度，`employee_id` 为空，进入公司待分配池。
历史负责人原样保留，不推测分配时间或操作者。搜索任务仍保存原请求者用于幂等和租约核验，
该身份不再自动成为新交付客户负责人。

只有当前在职 boss 可以搜索、分配及读取公司额度、任务、来源状态。HTTP 与服务门面
各自检查身份，服务门面每次从员工公共服务重新读取。manager/sales 只读自己负责的客户，
不扩展到下属；未分配客户仅对 boss 可见。平台额度修改权限不授予企业。

`assign` 每次在同一数据库事务内核验同公司在职 boss 操作者和 boss/manager/sales 目标，
先锁公司额度，再按员工和取得记录 ID 的稳定顺序加行锁。批次最多100条，记录必须唯一。
整批遇不存在、异企业、离职目标或归属冲突即回滚。同负责人重试幂等；不得覆盖其他负责人，
本次不提供转派。分配记录 `assigned_at`、`assigned_by`，不会再次增加交付额度。

同企业 canonical domain 仍只有一份取得记录。已有私有 ProspectAccount 的 OwnershipLock
归他人时，分配必须拒绝。应用层注入 `InventoryAssignmentBridge`，用已有 AsyncSession
装配潜客和员工公共服务，原子创建/复用私有 account 与归属锁，并保存 `account_id`；
不能先提交库存再用独立事务创建客户。同负责人历史记录缺映射时可显式幂等修复，
不得自动换负责人、补造历史审计或把公开邮箱认定为已验证。真实 API 必须装配该桥接。

## 数据隔离与迁移

0075 将负责人改为可空，增加可空分配审计及 account 映射；account 外键含 tenant，
公共池许可、去重、原证据快照、公司额度和 worker 租约语义保持。公共池不加入私有沟通事实。

升级不清除或重分配历史客户。降级只接受完全符合旧契约的数据；遇待分配客户、分配审计
或 account 映射必须拒绝，避免填造负责人或静默丢失业务事实。不得靠清空字段绕过降级保护。

## 验证

定向测试覆盖员工/经理搜索拒绝、当前老板撤权、仅本人读取、未分配交付、旧归属、目标资格、
批量回滚、并发单负责人、幂等重放、额度不变、既有客户冲突、桥接异常回滚和迁移往返。
PostgreSQL 验收仅使用测试进程独占容器和 UUID 空库，不访问运行数据库或真实客户。

## 已分配客户接入现有闭环

standalone库存必须注入真实CustomerAssignmentBridge。同一调用方session构建公开
Prospecting resolve_account与Employee resolve_owner；借用UoW仅flush，所有提交/回滚/关闭
归外层批量分配。历史同owner重试仅补account_id，保留原分配审计和交付额度。

客户应用通过tenant-bound当前身份/取得/归属guard，再调各域公共读写服务。
员工使用NO KEY UPDATE锁兼容Outreach外键，取得与归属读锁持有到公开Outreach事务结束；
这不是跨域全事务提交，Outreach自己的幂等键与状态恢复仍是事实来源。
实际归属冲突使普通员工私有读写失败关闭，boss可读并看到冲突，不能代员工启动。

新增只读`assess_enrollment`复用当前精确审批、联系人、抑制、已有序列、额度、发件身份和回复
事实。选项中的可启动联系人ID只代表读取时门禁通过；实际enroll仍在其自身事务现查。
新增Demand精确account有证据活跃假设接口，强制写入Enrollment.source_hypothesis_id；
缺证据不造假设，后续回复沿原绑定来源读取。配置缺失保持具体阻塞，不创建假verified、
审批、企业类型或政策。manager的旧机会/收件箱身份范围同步收紧为本人。

自动跟进能力需独立的显式组合参数（默认关闭），不能从manual_send存在推断。
正式API和scheduler入口共享reply_enabled及Gmail/员工绑定检查。sender就绪判断与入组
复用确定性轮转和未知资格失败关闭；新入组在联系Quota预占之前与只读就绪共用精确回复门禁，
已有原key仍按首次记录重放，不把新门禁变成重复入组或额外额度消耗。


## 原命令核对的补充决定（2026-10-14）

跟进未知结果只能以原键及完整body显式核对。Outreach公开只读`replay_enrollment`契约：
按当前身份的精确tenant/account/campaign授权读取既有Enrollment，逐项核对
campaign/version/account/contact/source。合法命中返回当前原记录，不重查新增准入事实、
不创建Attempt、不预占Quota；错绑定拒绝。未命中返回None，组合层才经Demand/Outreach
完整新入组门禁执行。`enroll`自身在Campaign锁内也先核对原命令，再执行新入组门禁。
旧接口未提供version的兼容语义保留；客户接口仍强制提供精确version。

客户组合层只能调用这一公共契约，不能跨域读Outreach内部仓储；核对仍必须先经当前在职
身份、同企业取得记录和实际owner的guard。来源假设变成validated、证据/审批/联系人资格
失效、Campaign变更或运行能力关闭，只阻止新命令，不能抹去已存在原命令的事实。

前端新命令先成功持久化精确原key/body再POST；存储读取或写入异常失败关闭为未提交，
不替换其他未知原请求。未知结果的恢复遇当前条件拒绝继续保留原依据；身份变化或403
仍清除保护视图。自动轮询只更新任务与额度，分配列表由显式刷新或提交后刷新更新，
实际提交始终由后端在锁内重新核验当前员工及归属。

## 单客户手动入组

Enrollment增加不可变`execution_mode`，仅允许`automatic`与`manual`。历史记录与省略模式的
原请求均为automatic；模式参与原幂等命令绑定，不能借同key重试把手动客户改成自动序列。
模式不改变Campaign批准边界，也不授予员工修改老板配置的权限。

客户follow-up POST显式选择manual时，不要求自动跟进装配已开启；其余当前员工/实际owner、
同客户有效证据假设、精确Campaign版本批准、VERIFIED联系人、抑制、回复、额度、发件身份
门禁全部复用。GET follow-up支持同名模式查询，缺省仍automatic；只读就绪只去除该模式
不需要的自动装配阻断，不能把只读结果当成发送许可。客户详情继续如实展示自动装配状态。

manual记录可以经原人工prepare/send入口推进，实际发送仍走原Gateway与当前事实复核。
scheduler到期查询在SQL中只取automatic；人工完成一步后即使next_send_at到期，manual也
不进入自动扫描。本切片不开放模式修改或自动化升级操作。

迁移0076线性承接0075：非空模式列默认automatic并设CHECK约束。任何manual记录存在时
降级必须失败且保留原数据，包括已经停止/完成的记录；禁止静默删除模式后让旧scheduler
误认人工意图。升级须按现有操作纪律同步部署API与scheduler，不允许混用忽略新列的旧worker。
