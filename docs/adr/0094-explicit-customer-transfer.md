# ADR 0094：管理员显式转交已有客户

日期：2026-10-14。状态：按用户本轮明确要求实现；实际发信单独核验。

## 背景

用户要求使用 jslt 界面将已取得的 Simba 客户交给 qikai，并使用
sales@jslingte.com 联系。ADR0093 的首次分配禁止覆盖已有负责人，因此需要独立转交命令，
不能放宽普通分配使任何旧请求都能覆盖归属。

## 决定

- 客户详情提供管理员专用转交表单，选择同企业在职 boss/manager/sales 并填写原因。
- 新接口接受目标员工、期望原负责人、期望分配时间和原因。当前企业及操作者取会话，
  HTTP、领域门面及锁内均校验。期望值不符返回409；未知结果刷新核对，不自动重发。
- 采用已有额度→员工→取得记录→账户→归属锁顺序；同事务调用员工域 transfer，
  更新取得负责人及分配时间，追加原负责人/目标/操作者/原因历史。分配时间严格递增，
  阻止A→B→A后陈旧页面再次执行。无需新增表或迁移，不重复扣交付额度。
- 已有关联账户是前置条件；真实归属和取得负责人不一致时拒绝。活动跟进须先停止，
  不把原员工的发送序列隐式交给新员工。
- 保留所有联系人验证、商业事实、发件配置与触达门禁；转交不验证邮箱、不批准开发任务、
  不伪造发件身份、不触发发送。首次分配的同owner幂等、冲突拒绝规则不变。

## 验证

真实PostgreSQL覆盖归属与历史原子更新、额度不变、失败回滚、越权与陈旧命令拒绝、
来回转交后的旧命令拒绝、活动跟进阻断，以及原普通员工私有详情访问失效。
前端覆盖真实表单目标过滤及原版本提交；实际部署及UI操作另记验收。

## 并发补充

- 转交在既有员工→取得记录→账户→归属行锁之后取得 Outreach 已有的
  tenant/account advisory transaction lock，再查询活动 Enrollment。入组先取原
  idempotency-key 锁再取同一账户锁；锁保留到事务提交。不能把转交账户 advisory
  提到归属行锁之前，也不能在入组取得 advisory 后再取归属行锁，否则会与客户详情
  guard 的锁序相反。
- 账户发现的分配步骤保存员工域返回的 `owner_id`、`owner_locked_at`；v1/v2 入组均须
  将该真实版本作为 `EnrollmentOwnershipBinding` 传入。Outreach 在账户锁内读取并
  比较当前归属，不改变已存在 Enrollment 的只读幂等重放。历史任务缺少绑定时失败关闭，
  不把当前负责人或时钟补成历史授权；需要重新明确安排。客户工作台已有的持锁 guard
  保持生效，普通分配的幂等与冲突行为不变。
- 本转交入口更新 OwnershipLock 的时间也严格递增，固定时钟下 A→B→A 不能恢复旧任务授权。
- 停止 Enrollment 不能取消已经认领的 Connector 调用。存在 `sending` Attempt 或同账户
  canonical `email.send` 的 claimed/executing/failed_transient/待对账事实时拒绝转交；
  只读核对成功后才能重新提交，不撤销 claim、不重发、不更改 Gateway 管线。
- 多连接 PostgreSQL 验证两个入组/转交先后顺序、固定时钟来回转交、停止后的在途发送、
  Gateway 执行与停止/转交交错，以及已完成发送允许转交。测试只使用受控发送端口。
