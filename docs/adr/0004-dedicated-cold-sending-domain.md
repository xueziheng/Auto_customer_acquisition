# ADR 0004：冷开发使用独立域名，与主业务域名物理隔离

- **状态**：已接受
- **日期**：2026-08-07

## 背景

系统要按每天 50–100 封的量级发冷开发邮件。冷邮件天然伴随较高的退信率和投诉率——即使数据质量做到最好，也总会有失效地址、也总会有人点「标记为垃圾邮件」。

邮箱服务商的信誉判断是**按域名和 IP** 做的，不区分「这封是冷开发、那封是合同附件」。一旦域名被标记：

```text
开发信进垃圾箱            → 业务停滞，但可以换域名重来
与现有客户的往来进垃圾箱   → 客户以为你不回邮件
报价单、合同附件收不到     → 直接损失订单
```

后两条是「公司邮箱废了」级别的事故，恢复周期以月计，且期间无法通过技术手段绕过。

## 决策

冷开发使用**独立注册的域名**，与主业务域名物理隔离：

```text
company.com            主业务。人工往来、合同、报价。永不用于冷发送
outreach-brand.com     冷开发专用。烧了就换，不影响主业务
```

同时把发件身份提升为独立业务域 `domains/sending-identity/`，包含预热状态机、认证配置门槛、信誉指标与自动熔断。

## 理由

这是**风险隔离**，不是优化。冷发送的信誉风险不可完全消除，只能选择让它落在哪里。落在一个可抛弃的域名上，代价是换域名的麻烦；落在主域名上，代价是主营业务中断。

原设计稿把「发件域名信誉」列在合规条目里，与「退订入口」「退信处理」并列。这个定位偏低——其他条目出问题是合规瑕疵，这一条出问题是业务停摆。所以它需要独立的域、独立的状态机、以及自动熔断（不等人工响应）。

**不用子域**（如 `outreach.company.com`）：子域的信誉问题会连带影响父域，隔离不彻底。

## 放弃的选项

**用主域名的子域发送。** 配置最简单，且能沿用已有的域名信任。但隔离不彻底——子域被标记会影响父域，这就失去了隔离的全部意义。

**用第三方发送服务的共享域名。** 完全不碰自己的域名，但邮件会显示第三方域名，B2B 场景下信任度低，且共享 IP 池的信誉受其他客户行为影响，自己控制不了。

**只做监控，不做隔离。** 靠把退信率控制得足够低来保护主域名。问题是投诉率不完全可控（客户心情、行业敏感度），且一旦触发标记就已经晚了——这是不可逆的风险，不能靠事后监控管理。

## 后果

- 需要额外注册和维护域名，配置 SPF/DKIM/DMARC。**预热期意味着新域名前几周发量很低**，这是必须接受的启动成本。
- 冷开发域名与主域名品牌不同，客户可能产生疑虑。缓解方式：域名与主品牌有可识别关联，邮件签名中说明公司主站。
- 员工手动回复要用 `human_reply` 用途的独立身份，与冷开发身份分开——人工往来不应受冷发送信誉波及。这增加了配置复杂度。
- 域名被烧后要能快速换。**换域名流程要提前演练**，不要等出事才发现要三天。

## 何时重新审视

- 冷开发域名连续稳定运行且退信率、投诉率长期远低于阈值：可以考虑增加身份数量提高发量，但**不改变隔离原则**。
- 如果转向以 opt-in 为主的获客方式（内容营销、落地页留资），冷发送量下降，届时可重新评估是否还需要独立域名。
- 隔离原则本身不建议放宽——这条决策的收益是「避免灾难」，而灾难的概率无法降到零。
