# ADR 0113：企业资料与已确认产品驱动获客，沿用 Codex CLI

- **状态**：已接受（产品方向与运行引擎选择）；整体升级尚未实施验收
- **日期**：2026-10-21

## 背景

用户在本次讨论中明确选择“企业已确认产品优先，围绕产品开发客户”，随后补充完整流程：每家企业上传自己的资料，形成自己的数据库；企业选择地区、产品等条件，Agent 自动搜索获客、获取邮箱并持续进行邮件沟通。平台管理者配置各企业使用的模型 API，企业不能修改这些配置。

当前工作区仍有需求优先的总纲与下级规则。另一份验收源码的 ADR 0081 已记录产品驱动的决定，但源码与部署基线尚未统一。本决策依据本次用户确认生效，不依靠副本的新旧推断授权，也不将副本实现标记为当前工作区已具备。

用户同时明确沿用 Codex CLI。本轮不引入 PenguinHarness 运行依赖，不把框架替换或对照实验列为升级前置任务。

## 决策

主流程为：企业上传资料并确认可用于客户开发的产品 → 选择产品、地区及其他获客条件 → 在获准范围内搜索客户 → 获取并验证联系邮箱 → 在批准的 Campaign 内发起联系 → 根据回复自动进行普通业务沟通 → 形成已验证需求并按规则交给员工。

1. 企业资料与提取结果按企业隔离。原件、提取字段与确认状态分别留存；上传文件不等于确认其中每条内容，Agent 不能自行确认产品、补造规格或认证。缺少必要资料时提示补齐。
2. 本企业已确认可用于客户开发的产品约束探索范围；模型可以研究应用场景和客户类型，但相关性仍是待验证推断。未确认候选产品与泛供应能力不自动成为默认获客目标。
3. 地区、产品等搜索条件形成可核对的目标。启动新 Campaign 须按既有流程批准；批准范围内的普通研究与邮件沟通不因每次调用模型而重复要求人工确认。
4. 找到邮箱只得到联系人线索；可达性验证、抑制名单、发送身份、配额、权限及适用政策检查通过后才能进入发送序列。所有外部动作仍经 Tool Gateway。
5. 收到回复后停止原开发序列，由回复流程在授权范围内接续沟通；不能一边聊天一边继续原来的冷开发催促。退订或明确拒绝应停止触达。价格、交期等商业承诺及成交/失败确认仍按根总纲审批。
6. 搜索匹配不等于客户有采购需求。需求假设、客户明确表达的已验证需求、满足条件的贸易机会继续分别记录，并保留 Provenance。
7. 沿用 Codex CLI 作为受限执行器。企业身份、数据权限、长期任务、预算、审批和工具执行仍由 TradeOS 管理；平台为企业绑定模型连接，真实凭证不暴露给模型或其执行环境。

九条全局硬边界、合格贸易机会定义与北极星指标均不变。此决策不扩大当前部署的已验收范围，也不自动授权真实发信、生产迁移或付费试验。

## 理由与取舍

产品作为入口使企业能够用自己的业务资料和明确的搜索条件驱动获客，符合用户确认的产品用法。需求验证仍用于判断客户是否值得投入，防止将产品相似性当成购买意愿。

代价是资料质量与产品确认成为前置工作；产品信息缺失、过时或分类错误会影响搜索。需要记录产品与任务的关联及资料版本，并允许员工纠正。跨目录需求可以记录并交给人工评估，不能借此静默扩大获客范围或许诺新供应能力。

沿用 Codex CLI 可保留现有适配工作，但不自动解决跨天任务、隔离和邮件会话恢复。应验证既有工具桥接与流程，不把这些问题归因于“缺一个框架”。

## 放弃的选项

- 无产品范围的需求优先探索作为默认入口：与本次确认的使用方式不符；未来如需独立市场探索，应另行定义范围与授权。
- 自动调整需求优先/供应能力探索配比：旧策略不再是默认产品路线；历史配置与运行记录保留，不能静默重解释。
- 接入或替换为 PenguinHarness：本次不采用；仅保留调研资料。除非出现明确且可复现的能力缺口，并重新评估，否则不启动迁移。

## 落地与验收

先统一代码基线，当前工作区与验收副本中的 ADR 编号存在冲突，须按内容和文件来源对照，不能只按编号覆盖。然后核查资料、已确认产品、搜索条件、客户与联系人、开发序列、回复会话、需求和人工接管之间的关联。

验收必须验证：不同企业资料不可串用；没有已确认产品时不会擅自补造；研究不擅自获得发送权限；未验证邮箱不进入发送序列；回复后原序列停止；普通沟通可持续处理；商业承诺转审批；任务恢复不重复发信；成本和失败原因可归属。

## 何时重新审视

企业明确要求跨产品市场探索、现有 Codex CLI 适配暴露可复现且无法合理修复的能力缺口，或真实运营数据证明资料入口与搜索方式需要调整时，另立决策。单纯更换开源框架不构成产品目标。
