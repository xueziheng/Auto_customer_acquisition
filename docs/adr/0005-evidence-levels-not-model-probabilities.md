# ADR 0005：置信度由代码依据证据等级推导，不存模型输出的概率值

- **状态**：已接受
- **日期**：2026-08-07

## 背景

原设计稿在多处出现这样的字段：

```yaml
confidence: 0.42
confidence: 0.67
confidence: 0.61
```

这些数字由大模型产生。问题是**大模型输出的概率值没有校准**——0.67 不代表「这件事有 67% 的可能为真」，它只是模型在生成那个 token 位置上倾向于输出的数字，受措辞、上下文长度、示例影响，同样的输入换个问法就会变。

而设计稿第八节那张证据等级表恰恰是**对的东西**：

```text
Agent 从行业推断            低
公开企业变化信号            中低
员工认为可能需要            中
客户回复表示感兴趣          中高
客户明确给出规格            高
客户给出数量、时间和目的地   很高
客户请求样品或正式报价      极高
```

这张表描述的是「证据的性质」，是可判断、可核对的事实。

## 决策

模型只做一件事：**判断某条证据属于哪个等级**。

置信度由**确定性代码**依据集齐的证据推导，输出**离散档位**，不是小数。推导规则见 [05-data-plane.md](../architecture/05-data-plane.md#三证据等级--置信度推导)。

数据库层面：`demand_signals`、`need_hypotheses` 等表**没有 `confidence` 数值列**，只有 `evidence_level` 枚举列。这条写进项目总纲成为硬边界 3，并由 `agent-runtime/guardrails/` 在写入前拦截。

## 理由

**可解释。** 「这条假设是中低档，因为唯一证据是一条公开的工厂扩建公告」——老板能看懂，也能判断要不要投入。而「置信度 0.61」无法追问。

**可回溯。** 档位由规则推出，规则可以单测。有人质疑某个判断时，能重放推导过程。模型输出的小数无法重放。

**避免虚假精度。** 存了小数，就会有人比较 0.67 和 0.71 谁更值得做，还会有人拿它算加权平均、设阈值。这些操作在数字本身没有校准的前提下全部无意义，但看起来很像数据驱动决策。

**换模型不影响历史数据。** 证据等级是对事实的分类，换模型后同一条证据的等级判断应该一致；而概率值会随模型版本漂移，导致历史数据不可比。

## 放弃的选项

**直接用模型输出的概率值。** 实现最简单，看起来最「智能」。但如上所述，这些数字不可靠且诱导误用。

**用模型概率值但做校准。** 理论上可以收集真实结果做校准（例如 Platt scaling）。但校准需要大量带标签的历史数据，Phase 1 一条都没有。且校准要按品类、国家、证据类型分别做，数据需求量更大。这是有了几百条成交数据之后才能考虑的事。

**完全不表达置信度，只列证据。** 最保守，但排序需要一个可比较的量——寻源队列和触达队列都要决定先做哪个。离散档位是可比较的最小实现。

## 后果

- 推导规则需要人工设计和调参（多少条同级证据能上浮一档、新鲜度窗口多长）。这些是**业务判断**，应该由人定并记录在案，不是让模型猜。
- 档位粒度较粗，同一档内的候选无法用置信度区分。这是有意的——同档内应该按订单价值和供应可获得性排，见 [09-scoring-and-feedback.md](../architecture/09-scoring-and-feedback.md#二phase-1-打分三因子)。
- Guardrail 要能识别并拦截模型输出的概率值，包括藏在自由文本字段里的（例如「置信度约 70%」写在说明里）。

## 何时重新审视

积累足够的成交与失败数据后（数百条量级，且覆盖多个品类和国家），可以：

1. 用历史数据回测各证据等级的实际转化率，据此调整档位权重
2. 评估是否需要更细的档位划分
3. 如果那时仍想用连续值，前提是**用自己的历史数据训练一个校准模型**，而不是直接采信大模型输出

无论如何，**「模型直接输出概率值并落库」这条永不解禁**。
