# ADR 0081：本企业产品获客与企业数据强制隔离

日期：2026-10-07。状态：用户已明确要求，实施中。

## 背景

用户要将 TradeOS 提供给多家企业；每家企业先完善并确认自己的产品，再围绕这些产品寻找客户。根总纲原来的需求优先起点已不符合本次明确要求。原有单企业装配和查询过滤不能替代数据库与资料任务的强制隔离。

## 决策

业务入口改为本企业已发布产品驱动客户探索；沟通后才形成已验证需求，九条全局硬边界和合格贸易机会定义不变。固定企业 app、worker、产品、资料、Obsidian vault、检索、会话及缓存均不得跨用企业资源。平台只读审计访问不授权 JSLT 的业务任务读取其他企业资料。

PostgreSQL 业务运行使用每企业专属的低权限登录角色；角色名为 tradeos_t_ 与企业编号 SHA-256 前 48 位 hex 拼接。RLS 同时控制现有行和新行，将 current_user 与行企业对应角色比较，不从可修改的请求字段或数据库 GUC 推断授权。保留应用查询 tenant 过滤、复合外键与原员工负责人授权。迁移账户具有管理能力，只用于可信部署流程，不能作为安全多企业运行账户。所有 tenant 表 ENABLE/FORCE RLS；缺策略、错误角色和特权运行账户使隔离启动检查失败。

关闭无过滤运维查询后门；平台统计仍须按指定企业分别查询并留痕。现有 0069 历史迁移的全库兼容性检查不扩散到业务运行路径。

## 取舍与限制

当前共享一台服务器和数据库服务；每企业不常驻整套容器。固定角色池避免通过复用连接 GUC 串租户，但企业数增长后需要管理连接总量。数据库管理者仍持有运维管理权限，RLS 不替代主机权限、对象存储授权或员工级客户权限。当前用户不启用业务备份，不在本轮改变该选择。

资料快照适配器不是完整产品上传、检索或网页 Codex 功能；平台三身份、邀请和管理界面也不能以隔离基座测试代替。上线报告逐项区分实现、验收和未接入能力。
