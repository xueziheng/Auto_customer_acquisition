# ADR 0002：Phase 1 只做需求验证闭环

- **状态**：已接受
- **日期**：2026-08-07

## 背景

完整设计覆盖了从需求发现到成交的全链路，还包括积分计费、多租户、桌面端、WhatsApp。全部做完是一个很长的周期，而在此期间**没有任何东西能验证核心假设**。

这个项目最大的未知是：**系统到底能不能自动发现真实需求？** 如果答案是否定的——比如发现的信号大多是噪音、冷邮件回复率过低、客户不愿意在邮件里谈需求——那么后面的寻源、成本、报价、计费全都建立在沙上。

## 决策

Phase 1 范围锁定为：

```text
Demand Signal → Need Hypothesis → 触达 → 回复识别 → Validated Need → 人工接管
```

寻源、成本、报价**由人工完成**，但相关数据结构与门禁（尤其是 indicative/quoted 价格分离、成本项清单）先建好。

## 理由

这条链路是**唯一能回答核心假设的最小闭环**。它端到端穿过了所有高风险环节：信号质量、联系人可达性、域名信誉、邮件回复率、需求提取准确度、人工接管衔接。

寻源与报价虽然工作量大，但风险低——它们是「已知怎么做，只是要写」的工作。而且 Phase 1 期间已验证需求可能只有个位数，人工处理完全来得及，自动化没有回报。

先做低风险高工作量的部分，是典型的资源错配。

## 放弃的选项

**先做产品与供应中心（淘宝式产品卡）。** 它看得见、演示效果好，但它是供应能力清单——如果没有需求进来，做得再漂亮也没用。而且它会诱导团队回到「拿现有产品找买家」的旧思路，正是本项目要纠正的东西。

**先做 Boss 指令与控制台。** 自然语言指挥很吸引人，但在没有真实数据流的系统里，指令没有可指挥的对象。

**全链路同时开工。** 人力不够，且会导致每条链路都半成品，无法端到端验证任何东西。

## 后果

- Phase 1 期间寻源与报价是人工的，员工体验会比较粗糙。这是有意接受的代价。
- 但**数据结构不能因为「反正是人工」而省略**。价格基准字段、成本项清单、Sourcing Case 状态机现在就要定好，否则 Phase 2 自动化时要迁移历史数据。
- Loss Reason、打分快照这类「为将来留数据」的机制必须 Phase 1 就有——它们的价值全在于历史积累。

## 何时重新审视

Phase 1 完成标准：能从零起一个 Campaign，产出至少一批已验证需求，每条都能点开看到原始证据，且发件域名信誉健康。

达到后评估：已验证需求的产出速率、每条的成本、人工接管的响应时长。这三个数决定 Phase 2 优先自动化哪一段。

如果 Phase 1 发现核心假设不成立（例如信号噪音过高、回复率长期低于可用水平），**应该改的是发现与触达策略，而不是继续往下游建功能**。
