# ADR 0001：单租户运行，但隔离预埋

- **状态**：已接受
- **日期**：2026-08-07

## 背景

系统最终要卖给多家贸易公司（Phase 3 的 Managed Shared 与 Managed Dedicated）。但 Phase 1 只有自己一家公司在用，最大的风险是「需求验证闭环到底跑不跑得通」，不是多租户。

问题在于：多租户隔离是那种**事后补极其昂贵**的东西。一旦有几十张表和几百个查询是单租户假设写的，再加 `tenant_id` 需要逐个审查每条查询，且漏一条就是跨租户数据泄露——这类缺陷在测试环境几乎发现不了。

## 决策

Phase 1 只跑单租户，**但从第一张表开始就带 `tenant_id`，所有查询强制租户过滤**。这条写进项目总纲成为硬边界 8。

Phase 3 开启多租户时，工作量应该只是「打开开关 + 做隔离专项测试」，而不是数据模型改造。

## 理由

隔离的成本是**不对称的**：现在加，每张表多一个字段、Repository 层统一注入过滤，成本接近零；以后加，要审查全部查询路径，且失败模式是静默的数据泄露。

面对这种不对称，即使多租户还很远也应该先付这笔小成本。

同时，不做多租户的**功能**（租户管理、订阅、配额隔离、按租户计费）——那些确实可以等，因为它们是加法，不是改造。

## 放弃的选项

**完全单租户，以后再改。** 省下 Phase 1 的一点点工作量，代价是 Phase 3 要做一次高风险改造，且改造期间新功能开发要停。不值得。

**Phase 1 就做完整多租户。** 会引入租户管理、配额隔离、按租户的资源限制等一整套功能，分散对核心假设的注意力。多租户的难点不在数据模型（那部分我们现在就做了），而在运营与计费，那些可以等。

## 后果

- 单租户期间 `tenant_id` 是个恒定值，看起来冗余。**不要因此把它省掉或允许某些表例外**——例外就是以后泄露的入口。
- Repository 层需要统一的租户过滤注入机制，不能靠每个查询点自觉。这是 Phase 1 就要建好的基础设施。
- Code review 要把「有没有缺租户过滤」作为固定检查项。

## 何时重新审视

Phase 3 开启多租户前，做一次隔离专项测试：故意构造缺失租户条件的查询，确认能被拦下；构造跨租户 ID 引用，确认被拒绝。测试通过才允许接入第二家租户。
