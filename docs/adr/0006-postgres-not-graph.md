# ADR 0006：暂不引入图数据库

- **状态**：已接受
- **日期**：2026-08-07

## 背景

系统的核心数据是一张关系网：客户 — 需求 — 产品 — 供应商 — 员工 — 证据。而且有些查询天然是图形状的：

```text
这家家具制造商可能需要哪些上下游产品？
和这家企业相似的公司还有哪些？
这个需求簇涉及哪些客户、哪些国家、可以由哪些供应商满足？
哪些员工处理过类似的客户和需求？
```

看起来很适合图数据库（Neo4j 之类）。

## 决策

Phase 1 到 Phase 2 都用 **PostgreSQL 的关系表加 JSON 字段**，配 pgvector 做语义召回。不引入图数据库。

## 理由

**当前的"图"其实很浅。** 上面那些查询大多是一到两跳：客户到需求、需求到供应商、企业到相似企业。两跳以内的关联查询关系型数据库处理得很好，JOIN 加索引就够。图数据库的优势在深度遍历和路径查找（六跳、任意深度、最短路径），我们目前没有这类需求。

**多一个数据库就是多一套问题。** 双写一致性、跨库事务、两套备份、两套监控、团队要熟悉两种查询语言。而收益在当前查询模式下接近零。

**产业链推断不是图查询问题。** 设计稿里「家具制造商可能需要五金件、铰链、滑轨、包装」这类推断，本质是**模型基于领域知识生成的假设**，不是从已有数据里遍历出来的。这部分靠 `demand-intelligence` 加品类关系表（一张普通表）就能支撑，不需要图。

**JSON 字段能吸收结构不确定性。** 需求规格、产品属性这些字段随品类变化很大，JSONB 加 GIN 索引比预先设计图模型更灵活。

## 放弃的选项

**Phase 1 就引入 Neo4j 或类似产品。** 提前为可能的复杂查询做准备。但这是典型的过早优化：为想象中的查询付出真实的运维成本，而那些查询可能永远不出现，或者出现时形态与预想不同。

**用 Postgres 的递归 CTE 模拟图遍历。** 这实际上是保留选项——真需要有限深度遍历时，`WITH RECURSIVE` 能处理，不必立刻上专门的图库。

**用 Apache AGE（Postgres 的图扩展）。** 比独立图库轻，值得作为将来的中间选项。但现在同样没有需要它的查询。

## 后果

- 关系查询的 SQL 会比图查询语句啰嗦一些，尤其是需求簇相关的多表关联。可以用视图或 Repository 层封装缓解。
- 如果将来真需要迁移，工作量不小。为降低这个风险：**关系数据保持规范化，不要把关联关系埋进 JSON**。JSON 用于存实体自身的可变属性，不用于存指向其他实体的引用。这条要在 review 时把住。
- 相似企业查找（Lookalike）在 Phase 1 主要靠 pgvector 的向量相似度，而不是图结构相似度。这实际上更适合当前场景——相似性来自描述文本，不来自连接结构。

## 何时重新审视

出现下列任一情况时评估引入图能力（优先考虑 Apache AGE 而非独立图库）：

1. 出现需要三跳以上遍历的真实业务查询，且用 SQL 写出来难以维护
2. 需求簇与供应网络的关联查询成为性能瓶颈，且优化索引无效
3. 出现路径查找类需求（例如「从这个客户到这个供应商之间有哪些可能的贸易链条」）

**触发条件是具体的痛点，不是「数据量大了」。** 数据量本身不是引入图数据库的理由。
