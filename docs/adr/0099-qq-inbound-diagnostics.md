# ADR0099：QQ 入站失败的分阶段脱敏诊断

状态：隔离实现，未发布；只使用合成数据验收。

## 问题

原 QQ 入站将连接、认证、查询和解析等异常统一为 InboundError，Gateway 只保留 unexpected。
单凭这个结果无法推断 QQ 的 HEADER 查询支持情况，也不能判断用户回信是否有问题。

## 决策

增加 shared 的固定诊断契约，供连接器与 Gateway 插件共享。仅允许阶段枚举、错误类别枚举、
协议状态白名单与有界毫秒耗时；不包含邮箱、凭证、游标、协议返回、邮件头、正文、原件、
异常字符串或异常链。对不在白名单的协议状态只记录 unknown。不启用全局调试日志。

连接器保留 InboundError 的原继承关系；诊断不改变 Gateway 错误分类、驱动永久阻断、
重试时间、UID 游标、指定 Attempt、精确邮箱对、权限复核或消息边界。
已知具体阶段的错误在外层传递时保留原阶段；其余页级完整性错误归 page。
正常跳过无关或不合规候选邮件不记录失败事件。

诊断只通过容量一且归属于当前异步任务的槽交付。受信 reader 在原 Gateway 完成失败记账后，
使用真实 tool_call_id 向既有 tool_call_events 追加一条事件。写入前再核租户、操作者、
工具名和失败状态。stage 为 inbound.<阶段>，rule 为 <类别>:<协议状态>，
category 沿用原调用；不创建新表，不改变 pipeline.py 或通用 stage 顺序。

这条补充诊断是原失败账本之后的最佳努力写入：它失败时保留原失败结果，
不得将永久错误变成临时重试；也不得释放成功页。原 Gateway 执行前审计失败仍阻断动作。
所以缺少诊断事件不证明该阶段成功。取消按原机制传播并清槽，不补偿发送或启动后台任务。

仅现有显式 adapter 组合启用诊断，默认 Gmail 组合行为不变。
数据库和审计只保存受信调用关联 ID，不保存原件引用或 provider 错误原文。

## 验证和发布边界

以合成 IMAP 响应、隔离 PostgreSQL、原 Gateway 和原游标驱动验证阶段、脱敏、归属、
失败停止、去重及原权限边界。测试不调用真实 QQ、不发送邮件、不调用外部模型。
模拟通过不代表 QQ 真实协议兼容，也不代表原两封真实回信已入库或识别。

本阶段不部署、不改生产配置、不重启、不重试原游标。真实根因仍需另行授权后，
在原 Attempt 和原两次回信范围内做一次有界诊断运行。
