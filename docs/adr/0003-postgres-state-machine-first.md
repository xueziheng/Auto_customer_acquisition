# ADR 0003：工作流先用 Postgres 状态机，暂不上 Temporal

- **状态**：已接受
- **日期**：2026-08-07

## 背景

贸易流程有大量长等待：客户几天后回复、员工明天上传聊天、经理稍后审批、供应商两天后确认、报价 24 小时后过期、客户下周确认数量。这些不能靠一次 Agent 对话完成，需要能跨天、跨进程重启存活的流程编排。

Temporal 正是为此设计的：工作流在崩溃、网络故障、服务重启后能恢复，LLM/数据库/API 调用放在 Activity 里，Workflow 本身保持确定性。技术上它是对的选择。

问题是它引入的运维与认知成本：需要跑 Temporal Server（或买 Cloud）、团队要理解确定性约束和重放语义、本地开发要多起一个重量级依赖、调试链路变长。

## 决策

Phase 1 用 **Postgres 状态机**：状态表 + `scheduler-worker` 定时扫描 + 幂等推进。

`workflows/engine/` 的接口设计成**可替换**：状态定义、转换守卫、超时、重试、等待人工这些概念在接口层就存在，换成 Temporal 时只替换实现，业务流程代码不动。

## 理由

Phase 1 的流程复杂度还很低——两条主流程（outreach-campaign、reply-qualification），状态数各在十个以内，没有复杂的并行分支或子工作流。这个规模用状态表加定时扫描完全够用，而且：

- 调试更直观：状态就在表里，`SELECT` 一下就知道卡在哪
- 本地开发只需 Postgres，不多起服务
- 不需要团队先学一套新的编程模型

**关键前提是接口可替换。** 如果为了省事把状态推进逻辑散到业务代码里，以后换 Temporal 就要重写业务，那这个决策就是错的。所以接口设计是这个决策成立的条件，不是可选项。

## 放弃的选项

**直接上 Temporal。** 长期正确，但 Phase 1 的流程简单到用不上它的能力，而运维与学习成本立刻要付。等流程真的复杂了再上，届时也更清楚需要它的哪些特性。

**用 Celery / RQ 加延迟任务。** 它们是任务队列，不是工作流引擎——没有状态可视性，没有「等待人工」这种一等公民概念，长等待要靠反复重新入队模拟。会比状态机更难维护。

**用 Airflow 这类调度器。** 面向批处理 DAG，不适合以业务实体为单位的长生命周期流程。

## 后果

- `scheduler-worker` 是单例进程（或需要分布式锁）。重复扫描会重复推进状态机，这是本方案最容易出的错。
- 幂等必须在设计上保证，不能靠「一般不会重复」。每个状态推进都要幂等键。
- 定时扫描有延迟（取决于扫描间隔），不适合亚秒级响应的流程。目前没有这类需求。
- 状态机表会长得比较大，需要归档策略。

## 何时重新审视

出现下列任一情况就应切换到 Temporal：

1. 单条流程状态数超过 20，或出现需要并行分支合并的流程
2. 需要子工作流嵌套（例如一个 Campaign 下每个联系人一条子流程，且要聚合结果）
3. `scheduler-worker` 的扫描成本或延迟成为瓶颈
4. 出现两次以上因幂等或重复推进导致的生产问题

Phase 2 会引入寻源与报价流程，届时重新评估——那些流程的等待环节更多、分支更复杂，可能就是切换点。
