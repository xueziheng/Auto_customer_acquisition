## 真实验收入口

`tests/integration/test_live_reply_acceptance.py::test_live_reply_corpus_and_business_chain`
默认跳过，且不会创建模型 Provider。启用时必须同时提供：

- `TRADEOS_REPLY_LIVE=1`。
- `TRADEOS_REPLY_MODEL_SETTINGS_PATH`：权限符合私有配置要求的绝对路径。
- `TRADEOS_REPLY_LIVE_MAX_CALLS`：操作者明确允许的调用次数，至少163。
- 配置内必须启用回复识别与模型数据外发，租户和员工的调用限额均至少163。
- 配置所指秘密引用通过原 `EnvironmentSecretResolver` 解析；不要把密钥放入命令参数、报告或聊天。

验收创建独立 owned 存储和合成员工，复用实际 standalone API 与 scheduler。
配置验证来自真实登录、API 与 scheduler 心跳，以及一次明确 probe。
Gmail 始终受控；不使用真实客户、日常发件身份或个人来信。

调用安排为一次 probe、原样160条分类、一次正向回复和一次明确退订，合计163次。
语料通过原入站事件形成160个不同的 canonical Run，再交给原 Gateway 分类器。
完成语料分类后取消这些评估专用 Run，再推进两个独立业务场景，防止二次派发。
不会自动提高限额或自动重试未知执行；重新执行整批会产生新的付费调用，需要重新核对剩余额度。

入口将报告保存为 `output/acceptance/reply-model/<本次ID>.json`，包括实际模型与配置版本、
生产投影说明、160题分母、逐题分类/动作/抑制范围及异常类别、字段提取召回、
业务效果、原始输入和期望的哈希、每次调用的实际账本计量。未知用量保持 `null`。

关键退订或投诉漏拦、自动回复误停、错误抑制范围、无证据建档阻止验收。
其他语义偏差也保持未完成，逐题记录；不修改冻结期望来让结果通过。

首次完整入口测试为1失败、16项原链路回归通过。失败原因是批量回填后仍需经过重复历史页，
原单消息fixture的固定三轮收件不足以读到新消息。入口现按指定新回复的唯一Message-ID等待流程终态，
最多推进20页，未修改生产游标或调用幂等规则；单独复验入口后通过。测试仍有一条已有SQLAlchemy弃用警告，
来自 `infra/db/repositories/compliance.py` 的 `distinct` 用法，不是本轮新增失败。

## 独立审查后的修复（2026-10-06）

独立审查范围为 `b5e4e78..4c4ed46`，结论为零项 Critical、两项 Important、零项 Minor。
两项重要问题均纳入本次修复，没有将受控测试或审查结果视为真实模型验收。

1. 评估适配器原先丢弃原件正文和证据分段，可能接受脱敏占位符的一部分，造成评估与生产不一致。
   现在生产分类步骤与评估共用同一证据校验函数；评估映射保留可信 reader 的完整不可变视图，
   只有当前 `subject/body` 发送给模型。新增占位符片段、跨证据分段和 Unicode 原话用例。
2. 宽泛关键词覆盖会把正确识别的投诉、自动回复或否定退订改为退订，也会因提及公司而扩大抑制范围。
   现在仅完整的当前退订请求句触发确定性覆盖，保留投诉类别；代码自动扩大账户范围时要求请求中明确包含群体目标。
   正确的自动回复和否定表达保持原分类，模型误判的明确退订请求仍受到拦截。

修复前七项新回归失败；进一步添加的明确账户退订用例也先复现失败。
最终分类、模型端口、评估适配器、原评估运行器与 live 配置前置检查共75项通过（1.00秒），
Ruff、七类结构自检及本批差异空白检查通过。冻结语料输入、期望及原评估运行器均未修改。

投诉持久化测试最初假设只有一条抑制记录。核对既有域规则后确认，回复处理和信誉反馈分别保留
一条相同联系人的不可变来源记录。因此保留两条记录，并断言目标、原因、来源以及重复处理不新增记录；
没有修改投诉动作表或删除任何抑制事实。首次业务回归19项通过，唯一失败是这个测试假设。
