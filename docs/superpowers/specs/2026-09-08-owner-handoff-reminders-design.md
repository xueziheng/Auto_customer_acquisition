# 待接管负责人周期提醒设计

## 目标与授权

依据已确认的[业务规则](../../operations/web-pilot-policy-decisions-2026-09-08.md)：待接管每两小时提醒，员工点击接受后停止提醒，员工归属不变。受众先按负责员工处理，不抄送经理和老板；这是已明示的保守假设。采用连续经过时间，复用现有 UTC scheduler，不建立工作时间日历。

本子项目只交付这一行为及真实持久化验证。主动退回与 Agent 接续、关闭金额分档、首次真实 profile 初始化不属于本子项目；既有业务政策缺项不能用测试默认填补。

## 全局约束

- 只提醒当前负责员工；不因超时改变负责人，不通知经理或老板。
- 提醒周期由操作者显式提供；本用户确认的值是 7200 秒，不作为隐藏全局默认。
- 仅对尚未接受的待接管事项提醒；员工接受提交后，后续扫描和通知投递不能再产生该事项的新提醒。历史已投递通知可以保留。
- 初始请求通知保留，重复提醒按持久轮次去重，进程重启和重复事件不造成同轮重复。
- 复用 Postgres Workflow、durable Outbox、通知任务和站内通知出口；不创建 Codex 自动化，不发真实邮件。
- 旧逐级升级模式显式兼容，已有运行不能被新定义静默重新解释；模式切换若不能安全兼容，必须明确拒绝或限定新 profile，并在文档说明。
- 所有查询保持 tenant 过滤；当前员工/接管状态从服务端事实读取；通知层不复制领域业务判断。
- 不输出真实或合成凭证、Cookie、DSN、私有配置、原始失败材料；测试材料仅留在进程内。
- 只改现有隔离工作目录，不推送、不合并、不删除历史 output，不修复共享 Git。

## 方案

新增明确的只提醒负责人模式，与原 T1/T2 升级模式区分。配置增加可选的显式负责人提醒秒数；缺省保持原入口行为，正数启用新模式。API 与 scheduler 必须解析/装配同一策略，pilot 私有配置必须持久保存并在停启时保留它，不能只有单元层支持而 runtime 忽略。

复用 `human_handoff` 的流程版本能力：原 v1 为逐级升级；新模式将整数周期秒数加一作为持久版本，输入范围为 1..2147483646 秒。当前类型的 2..2147483647 版本空间永久用于此结构的周期编码，未来结构调整必须新建明确 workflow type，ADR 记录此约束。不修改通用 engine。API 和 scheduler 实际启动均检查活跃同类型 Run：若版本与所选模式/周期不符（包括 v1 与新模式互换），固定拒绝，不静默悬挂或重新解释。操作者须恢复原配置完成旧运行后再切换；无活跃 Run 才允许选择不同模式。

接受行为已有 `HandoffAccepted`。新模式必须在事件尚未消费时也尊重数据库已接受事实；已排队但未投递的负责人提醒需要过时检查，不能仅依赖扫描停止。若存在接受与实际入站内通知的竞争，采用确定性的事务/锁或当前状态条件写入边界，避免先检查后投递的竞态。领域提供最窄的当前状态事实接口，apps/infra 负责装配，不允许通知网关直接导入域内部。

接管未接受但负责人已停用/改变时必须读取当前事实并安全拒绝旧受众；不能回退旧事件里的负责人。缺失事实或依赖失败不能假称已投递。新提醒使用明确原因码，模板不要称其为经理升级或 SLA 违约。

## 验收

使用可控 UTC 时钟，无需实际等待两小时：初始通知后，7199 秒没有周期提醒；7200 秒和14400 秒各一条当前员工提醒。相同到期轮次重复扫描与重启不重复；经理/老板没有被提醒，机会归属不变。

通过真实 PostgreSQL 接受路径验证：接受前已入队但尚未投递的提醒被抑制；接受提交而 Outbox 延迟时仍不产生新提醒；接受与到期扫描/投递竞争结果一致，接受后没有新站内提醒。重复接受、跨租户、旧 owner、不可用员工与原 v1 回归均须覆盖。

验证 profile → API/scheduler 解析 → 流程 → 通知任务 → 实际站内存储的装配链；不得把 fake notifier 列表当作真实站内投递。只在独立合成资源上运行，清理精确 owned 资源。
