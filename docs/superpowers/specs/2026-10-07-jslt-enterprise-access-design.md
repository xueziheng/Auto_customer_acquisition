# JSLT 平台与企业账号权限设计

日期：2026-10-07（北京时间）
状态：待用户审阅的设计；未实施产品功能，未变更线上账号或数据库。
开发位置：阿里云 `/srv/tradeos/development/TradeOS`，分支 `codex/jslt-enterprise-access`。
生产基线：`20261007-model-v4`；Git 导入基线 `7a53233a96b8aa9258ff77a0e98a66bd51d0f80d`。

## 1. 用户目标与已确定约束

用户希望 JSLT 经营 TradeOS 平台，同时 JSLT 自己也使用贸易工作台；其他企业拥有自己的管理员和员工。公司资料共享，客户与跟进按负责人分配，不增加经理、销售、采购等必填职务。最高平台权限授予用户本人，不因为属于 JSLT 就自动拥有。

后续代码直接在阿里云开发、测试和部署，原电脑 WSL2 项目和数据不动。现有云端测试管理员保留；云端业务数据备份继续关闭。本设计不要求重新清空数据库，不导入原电脑数据，不发送真实客户邮件。

验收结果必须能演示：用户管理 JSLT 及另一家合成企业，两家企业各有员工；普通员工不能读取同事私有客户或其他企业数据，平台管理员能在独立入口查看企业情况；停用与交接能生效。

## 2. 推荐方案及取舍

采用一个个人登录账号、独立的平台授权、按企业绑定的成员身份。JSLT 和其他客户企业平级；平台控制范围与 JSLT 业务范围分离。你登录后有「平台管理」「JSLT 工作台」两个入口，普通成员直接进入自己的企业工作台。

相比两个独立管理员账号，这种方案减少重复登录，但必须给平台操作单独授权，并在跨企业查看时展示明确上下文。相比每家企业独立部署，它降低当前资源和维护成本，但必须先完成真正的多租户隔离验收。第一版采用共享应用与 PostgreSQL，文件存储按企业授权隔离，不用一家公司一套容器。

本批不包含订阅收费、积分钱包、自定义角色、组织树、公开自助注册、Obsidian 网页接入、联网搜索、新的模型供应商或替客户自动审批/发信。

## 3. 身份和数据边界

拟补入术语表的概念：平台管理员（Platform Administrator）、企业成员关系（Enterprise Membership）、企业邀请（Enterprise Invitation）、平台查看会话（Platform Inspection Session）。这些名称只描述新系统能力，不替换既有 Need、Trade Opportunity、Employee 等术语。

- 平台登录身份回答「这个人是谁」。密码和会话实现留在可信认证层，模型永不接触凭证。
- 平台授权回答「此人能否经营平台」。不从公司名称、邮箱后缀或 Employee 的角色推断。
- 企业成员关系回答「此人属于哪家企业、是管理员还是员工」。成员必须关联本企业 Employee，历史归属保持 Employee ID。
- 客户归属回答「本企业这个客户由谁跟进」。它不授予跨企业权限。

为保留所有表带 tenant_id 的硬边界，登录身份、平台授权、企业目录和平台审计放在独立平台控制租户内；每家企业的成员、员工、业务记录和文件元数据仍使用自己的业务 tenant_id。平台控制租户不是 JSLT，不能装配贸易业务流程。企业目录记录目标企业 ID，目录读取本身仍过滤平台 tenant_id。跨范围外键与身份解析的改变需先留 ADR，不能通过删除 tenant_id 或旧复合外键草率实现。

服务器依据已认证身份、当前成员关系或平台查看授权确定有效企业范围。浏览器传来的企业 ID 只用于选择，不能成为授权依据。进入工作台时服务端发行绑定企业和成员版本的会话；切换工作台轮换会话，旧上下文失效，并清理前端缓存及其他标签页状态。

第一版界面优先支持普通账号仅加入一家企业；身份结构允许未来多个成员关系。平台管理员本人可同时拥有 JSLT 成员身份，平台身份不自动成为所有企业的成员。

## 4. 角色与操作矩阵

| 操作 | 平台管理员 | 企业管理员 | 员工 |
|---|---|---|---|
| 开通、停用企业 | 平台入口允许 | 禁止 | 禁止 |
| 授予平台权限 | 首批仅可信初始化/恢复工具，网页不开放 | 禁止 | 禁止 |
| 邀请、停用企业成员、变更企业角色 | 首位管理员开通及留痕恢复；日常由企业管理 | 仅本企业 | 禁止 |
| 管理员身份交接 | 显式恢复流程，不能冒充原管理员 | 仅本企业，禁止移除最后一位有效管理员 | 禁止 |
| 公司档案、正式产品及标记为公司共享的资料 | 指定企业只读查看 | 本企业维护 | 本企业读取；可提交资料草稿 |
| 客户、需求、贸易机会及跟进 | 指定企业只读查看 | 本企业全部；可分配负责人 | 自己负责的客户及关联业务 |
| 员工上传资料和私人 AI 会话 | 不在首批平台查看白名单 | 按资料本身权限；不自动读取私人 AI 会话 | 本人及明确共享的资料 |
| 价格、报价、政策和其他高风险审批 | 平台身份不参与客户企业审批 | 按现有逐次审批及独立审批约束 | 可准备本人业务草稿，不能批准 |
| 凭证原文、他人密码 | 不提供读取界面 | 不提供读取界面 | 不提供读取界面 |

公司共享不等于供应商底价、凭证或所有客户都对员工开放。当前成本及敏感字段规则继续生效，需字段白名单的页面不能用整表 JSON 输出。平台查看明细的首批白名单为企业档案、共享资料、客户业务记录、已验证需求、贸易机会及其业务沟通；查看和文件读取逐项留痕，排除凭证及私人 AI 会话。

新建成员只提供 admin / employee 两种企业身份。旧七角色历史值保留可读；迁移必须按实际旧角色写显式映射与审计，遇到未覆盖的旧角色拒绝迁移，不自动扩大权限。不能让所有员工假扮 boss，也不能只把 sales 改成“员工”就宣称整个权限矩阵完成。已开放接口、服务层、工具网关和模型上下文必须消费一致的明确操作权限。

客户仍以 ProspectAccount 企业为归属粒度，同一家客户的联系人统一负责人。新客户默认分配给有权创建的当前员工；系统发现但尚无负责人时进入本企业待分配队列，仅企业管理员可分配。转交后旧负责人从新的请求开始失去业务读取权限，历史 AI 引用和附件读取重新判权；历史操作者署名保留。

## 5. 开通、邀请和账号绑定

### 企业开通

平台管理员填写企业名称和首位管理员的邀请信息。创建企业目录、业务租户和首位管理员邀请需要幂等处理；企业先处于待激活，邀请成功接受后可使用工作台。邀请失效或中途失败不会产生一个可使用的无管理员企业。

企业工作台激活不等于发信和自动化启用。公司资料、业务政策、邮箱连接、模型额度分别显示是否已配置；没有配置的能力保持关闭，不能复制 JSLT 的业务政策、凭证或额度到新企业。

### 首批邀请交付方式

当前云端没有用于账号验证邮件的事务邮件服务。为保证首批可落地，管理员点击「邀请成员」后复制限时一次性链接，自行交给指定人员；不在本批自动发送邀请邮件。

登录名在平台内唯一，企业显示姓名不作为身份。创建邀请时预留指定登录名；已有同名账号必须通过该账号登录接受邀请，不自动合并身份。邀请固定绑定目标企业、显示姓名、预留登录名和企业角色。新用户通过邀请设定自己的密码；已有账号必须先登录与预留登录名匹配的账号才能接受。企业与角色不能在接受页面修改。邀请令牌仅存摘要，明文只返回创建邀请的可信管理界面，不写日志、模型上下文或普通审计材料；兑换原子创建/绑定账号、成员和 Employee。链接过期、撤销、重复使用或目标不匹配时拒绝。

管理员登记的邮箱在未完成独立验证前只是联系资料，不能用于自动加入企业、合并账号、登录找回或标记“邮箱已验证”。界面明确显示「尚未验证邮箱」。邀请凭证只证明持有管理员私下交付的链接，不证明真实姓名或邮箱所有权。本批采用邀请凭证绑定，不冒充已完成邮件验证；正式验证邮件和自助找回是独立后续能力。

### JSLT 初始化和现有账号

使用可信的一次性初始化工具预留 `jslt` 平台账号与 JSLT 企业管理员成员身份，通过私有激活链接交由用户自行设置密码。初始化工具默认 dry-run，应用时要求平台尚无管理员，并用事务和唯一约束防止重复初始化；不设置公共默认密码。

JSLT 复用当前空测试环境的业务 tenant_id，避免再次重建数据库。现有 `test_admin` 保留为 JSLT 企业管理员，不自动获得平台权限，不复制它的密码到新账号。认证迁移保留受支持的密码摘要格式，撤销旧会话，要求重新登录。恢复通道只能由可信服务器管理入口生成新的单次激活材料，不能显示旧密码。

## 6. 停用、交接与审批

停用成员的第一步是撤销其企业访问及相应活动会话，不能因为客户尚未分配完而继续允许登录。客户交接可随后逐项幂等完成：转给选定活跃员工，或进入管理员待分配队列；留存旧 Employee、归属历史及在途状态。已有账号若未来属于其他企业，只撤销受影响企业的访问。

降权、停用与会话认证需具有明确事务顺序。提交后新请求、文件下载和模型上下文读取必须使用当前权限；已被接纳的外部请求不承诺撤回，但结果应用前重新核对状态，并把不确定执行保留待核对。企业停用后拒绝新工作台访问及任务启动；后台排队任务不再推进外部动作，平台保留只读核对入口。

最后一个有效企业管理员不能被普通成员管理流程停用或降权；需先完成管理员交接。暂停整家企业是平台独立操作，不受该限制。邀请链接接受期间企业或邀请已停用时必须拒绝。

现有 Playbook 提案仅 boss 可提交，而审批禁止自批；只更换角色名称会让一名管理员无法完成政策初始化。新矩阵允许员工准备并提交适用的政策草稿，由另一名企业管理员确认；管理员本人提交的受独立审批约束事项仍需另一位符合条件的管理员。公司档案和资料草稿无需业务审批。单人企业可使用不依赖政策的功能，不能靠伪造提交人、默认批准或平台代批绕过独立审批。角色仍只有两种，不新增经理或采购身份。

## 7. 平台总览与企业查看

平台首页显示企业状态、有效成员数、最近活动、任务成功/失败、模型调用和 token 用量、资料空间，以及可核实的已验证需求和合格贸易机会数量。数据有统计时间；不可用显示未知，不把缺失来源当零。成本来源未接通前不编造金额或“单位机会成本”。

汇总任务按受权企业目录逐家执行带 tenant_id 的统计，写入平台控制租户的统计投影；不得用无租户查询扫描所有业务表。平台操作也要审计身份、目标企业、动作、结果和时间。

「查看企业」需最近一次密码确认，并创建限时、仅指定企业、只读的查看会话。页面持续显示当前企业及只读状态。它使用专门的读取投影和白名单端点，不冒充该企业 boss；客户端添加写请求、换企业 ID 或复用过期会话均拒绝。进入 JSLT 正常工作台后恢复本企业成员权限，不继承上一家企业的上下文。平台查看不把客户企业资料复制给 JSLT，也不能交给 JSLT 员工或其 AI 会话检索。

## 8. 后端装配与部署范围

本次 SSH 核实的基线：认证在 `infra/authentication/service.py` 构造时绑定 tenant，API 在 `apps/api/standalone.py`、`authentication.py`、`identity.py` 固定核对部署租户；scheduler 在 `apps/scheduler_worker/standalone.py`、`runtime.py` 固定装配业务、邮箱和 AI。需增加受限的企业运行时选择，不能删除原检查后让调用者任意传 tenant。

依赖方向继续为 apps → workflows / agent_runtime → domains → shared。平台企业生命周期继续归 organization，成员与客户归属归 employees，跨域开户/邀请/停用流程放 workflows，认证和存储实现留 infra，公共身份契约留 shared。平台授权的具体业务校验不下沉成 shared 的业务逻辑；前端使用 OpenAPI 生成类型。

API 每次请求装配或取得只属于有效企业的服务上下文，缓存键包含 tenant 和配置版本；禁止复用另家企业的 authorizer、Playbook、邮箱或模型上下文。scheduler 保持单实例，用明确绑定企业的运行时逐家处理，租约、任务和幂等键带 tenant。文件对象键、上传下载授权、来源引用、缓存、事件通知和工具凭证解析同样绑定企业；共享模型连接也要独立记账与配额。

当前服务器资源有限，不为每家企业常驻一组进程或容器。重型集成测试使用独立合成环境、限制并发；不能同时启动多套完整测试栈导致线上资源耗尽。容量尚未压测，不对可承载企业数作数字承诺。

发布采用新的版本目录和应用切换，数据库迁移只能显式执行。默认追加兼容字段/表，不靠数据库回退恢复旧版本；代码回退可行性须在同一候选迁移上验证。已按用户要求停用的数据备份不会被悄悄恢复。开发目录只保存源码与版本记录，不复制业务数据库、对象资料或生产凭证。

## 9. 实施前的规则与兼容性处理

需先写 ADR，明确本批提前进入受控多企业阶段，并更新 ROADMAP、对应 AGENTS 范围、共享身份契约与权限文档；九条全局硬边界保持不变。

现存 `infra/db/base.py` 的 unsafe_cross_tenant_query 与 HANDBOOK 运维示例允许无租户业务查询，但根 AGENTS 要求所有查询租户过滤，存在规则冲突。根规则优先；新平台不使用该后门。实施时审计现有调用并消除已开放路径依赖，统一文档为按目标企业查询与审计，不能通过文字豁免放宽硬边界。

必须完成实际跨域角色使用清单，逐个开放端点验证角色与负责人授权；未覆盖的旧角色专属操作保持关闭并明确标示。完成界面邀请并不等于全部业务多租户验收通过。

## 10. 本批验收标准

1. JSLT 与另一家合成企业各有管理员、至少两名员工；你本人有平台授权和 JSLT 成员身份，JSLT 普通员工无法进入平台后台。
2. 企业首管理员邀请与员工邀请可正常接受；错账号、换企业/角色、重复兑换、到期、撤销、并发接受均拒绝或幂等返回原结果，不产生孤立账号或员工。
3. 企业管理员仅管理本企业；最后管理员保护、角色更改、停用、旧会话重放及多标签工作台切换均可验证。
4. 员工可读公司共享资料，不能读同事客户；客户的联系人、跟进、需求、贸易机会、证据和文件采用一致归属。转交后旧负责人通过 URL、列表、附件、搜索或历史 AI 引用均不能取回无权数据。
5. 跨企业 ID 替换在 API、文件、模型上下文、引用来源、后台任务和通知路径都被拒绝；两企业分别出现同一幂等键不发生串单。
6. 平台统计正确标明来源及时间；查看企业有审计、只读、限企业和过期限制，无法代客户发信、改资料或审批。
7. 邀请、企业停用与后台执行之间的并发失败不会扩大权限；账号撤销或企业停用后没有新的未经授权外部调用。
8. 旧 `test_admin` 迁移后仍可登录 JSLT、无平台权限；`jslt` 必须通过专属激活完成初始化。实际密码和令牌不进入日志或模型。
9. 原有真实模型回复链的代码行为保持兼容。权限测试优先使用合成数据和受控模型，不为角色验收重复跑收费模型全语料；没有真实邮件或新 Campaign。
10. 结构自检、相关后端/前端测试、迁移兼容和两个企业的网页验收通过后，才开放企业工作台及后台任务。未测项目在交付中列出，不能以只通过 CRUD 测试宣称隔离完成。
