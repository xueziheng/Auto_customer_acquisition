# Phase 2 后续交付一：成本与报价闭环设计

日期：2026-08-28。基线：本地 `main` 的 `95fcfb8`。

状态：用户已于 2026-08-28 确认本书面规格并授权开始实施；当前在独立功能分支逐项开发、测试和审查。
本文是设计，不是完成报告，也不是对真实报价、发信、付费调用、部署或推送的授权。

## 一、目标、前置条件与范围

在已有成本表和审批能力上，交付一条可用人工资料独立验收的链路：

```text
已验证需求关联的贸易机会
→ 人工确认供应商实报价与成本项
→ 确定性成本、利润测算
→ 锁定成本及依据，生成报价版本
→ 独立人工审批
→ 经鉴权取得客户版报价文件（不自动发送）
```

本批仍属于 ROADMAP 的 Phase 2，不新增阶段。免费来源获客首批不重做；寻源自动化、候选产品卡、
需求簇排序、联系人多源、探索预算自适应和接管反压分别作为后续交付。Temporal 仅按已有 ADR
触发条件评估，不因进入 Phase 2 就迁移。

已确认的后续寻源边界继续有效：使用已有供应资料和可合法读取的免费公开网页；询价先产草稿，
经人工确认才可发送。不购买来源，不绕过登录、验证码或访问限制，不把这次确认当成任何一封询价的发送许可。
本批自身不调用寻源或联系人 Provider。

### 本批交付

- Estimated / Quoted / Actual 成本版本、利润规则配置、可复现的 Decimal 测算和成本锁定。
- 供应商价格证据的结构化确认、报价版本持久化、审批关联及过期处理。
- 现有成本报价页面和审批中心接线；内部视图与客户版视图分离；客户版 PDF。
- 租户隔离、权限、幂等、并发与兼容验证，以及可区分受控和真实数据的验收记录。

### 不在本批交付

- 自动联系供应商、自动发客户报价、采购下单、收款、自动作出库存或交期承诺。
- 真实联系人验证、生产发信、客户成交确认；报价批准不改变机会为 won 或需求为 fulfilled。
- 在线税率/汇率/运费采购、自动税务判断、自动折扣、多币种并列报价。
- 跨产品合并报价及其成本分摊引擎。本批一个报价版本对应一个产品规格和数量档、一张成本表、
  一个报价币种；不将一张总成本表错误用于多个不同产品。既有多行 DTO 保留可读，新入口拒绝不支持的组合。
- INDICATIVE 采购价格的客户报价例外。本批遵守 quotations 域更严格的 QUOTED 行约束；保留已有
  成本风险接受记录的阅读和原只读检查语义，但不以此把网页价格改标成供应商实报价。

业务前置：利润政策须由老板配置；供应商资料和成本需有人确认；审批人须独立于起草人与机会负责人。
缺配置或人员时显示具体阻断原因，不植入默认利润率或自批后门。Phase 1 真实运营仍按 HANDBOOK
原标准验收，本批不能证明发现和触达策略已在真实客户上成立。

## 四、资料、确认与成本版本

### 4.1 价格与费用依据

新增不可变的结构化价格依据，由人工从授权上传或已有消息/资料中确认。至少包括：

- tenant、依据 ID、供应商身份引用、关联需求/机会、产品规格及计价单位。
- 适用数量或明确数量区间、MOQ、单价/费用、币种、价格基准、报价时间及有效期。
- 原资料 artifact/message 引用、哈希、原文定位及观察时间。
- 关键字段 Provenance：来源类型/ID、提取者/时间、确认人/时间。模型提取只能进入待确认区。

QUOTED 采购依据必须证明供应商针对该规格和数量的实报价。仅选择 `quoted`、提供一个非空 URL，
或引用无法按租户读取的 artifact 都不够；不自动从来源类型推断价款真实性。
费用依据分别记录费用适用条件和确认来源，不把人工估计标成供应商确认。

同一价格依据可用于其数量范围内的方案，但每张成本表固定一个规格和数量档。量纲、数量范围、
MOQ、币种不匹配或证据过期均阻断正式报价；不能自动换算箱/件或沿用另一数量档。
数量、目的地、规格、条款变化必须重新确认相关成本适用性。

### 4.2 版本语义

- ESTIMATED：允许参考价，内部测算；不构成真实客户需求或可对外承诺的价格。
- QUOTED：逐项确认成本、场景适用清单和锁定汇率；正式报价使用本批严格价格证据检查。
- ACTUAL：人工登记实际发生的费用并关联凭证；不自动由 QUOTED 复制成已发生事实。
  支持与原报价成本的差异对照。没有确认的实际收入时，不展示“已实现利润”。

沿用同机会、同版本类型的原子版本号分配。草稿成本可按现有规则追加，已锁成本不可修改，
修正通过新版本及前序引用留痕。旧成本表仍可读取；旧记录缺新证据时标为待补证，不能迁移时补造确认人或时间。

### 4.3 完整性与成本归类

完整成本必须对现有 22 类成本逐一有“适用且已确认金额”或“明确不适用及理由”的人工结论。
缺项不是零；模型只能提出建议。该严格检查用于新报价路径，不改变旧只读 readiness 的含义。

为了区分毛利、贡献利润和全成本利润，由老板确认版本化核算口径，将每个成本类型唯一归入：
货品直接成本、其他变动成本、固定/间接分摊。三组必须不重叠且覆盖全部成本类型，无隐含默认映射。
这是内部管理核算约定，不宣称符合任一国家的法定财务报表口径。初次配置不要求现在给出具体数值，
但未确认前相应利润测算保持不可用。

同一费用不得既计入“获客成本汇总”又计入数据/广告/API 分项。输入须声明汇总或明细口径，记录
成本来源/分摊引用；同一费用明细被重复计入时拒绝，不确定重叠需人工消除。一张原始账单可以包含
多项不同费用，不能只按 artifact ID 去重；需要原文费用明细与分摊范围的身份。数量不同的版本不能直接比较总成本差异。

## 五、确定性计算与政策

### 5.1 必需输入

计算输入由成本快照、核算口径版本、利润规则版本、报价方案和显式计算时间组成。
利润规则由老板确认，含品类（或明确的全局规则）、底线和目标利润率、生效时间、确认 Provenance。
品类规则优先；没有匹配的已确认规则就阻断。已有无确认来源的历史规则保持可读，不自动获得新路径授权。

规则更新只增新版本。历史报价按原绑定规则重现；新提交/新导出正式文件须同时检查当前生效规则，
若当前底线变高导致旧批准不再覆盖，则阻断继续使用，人工创建绑定新规则的报价版本后重新审批，
不能悄悄改写历史数字或对旧内容无痕补批。

报价单价精度、总金额精度和舍入方式须显式选择并锁定，不默认所有币种都是两位小数。
不调用在线汇率：人工确认的每条方向性直连汇率纳入快照。已有成本汇率仍为各币种到核算币种；
新增报价换算单独保存核算币种到报价币种的显式汇率，不改变旧元组方向，也不自动倒数或拼接。

### 5.2 公式与展示口径

令 Q 为确定的正整数数量；每项确认费用先按锁定汇率归一，再将整单项除以 Q，单件项不分摊。
三组单位成本为 Cg（货品直接成本）、Cv（其他变动成本）、Cf（固定/间接分摊），C = Cg + Cv + Cf。
下列金额均先在核算币种、同一数量口径下计算：

| 输出 | 明确含义 |
|---|---|
| 单位完整成本 | C；所有已确认且适用项合计，模型待确认项不参与 |
| 最低可售价 | C / (1 − 底线利润率)，这里是以销售额为分母的利润率，不是成本加成率 |
| 目标售价 | C / (1 − 目标利润率)，仅内部测算，不是供应商实报价或已批准客户价 |
| 单位毛利 | P − Cg |
| 单位贡献利润 | P − Cg − Cv |
| 单位全成本利润 / 全成本利润率 | P − C；(P − C) / P，UI 不将它标为毛利率 |
| 可折扣空间 | max(0, 1 − 最低可售价 / P)，只表示数学空间，不自动授予折扣权限 |
| 可追加获客成本空间 | max(0, P × (1 − 底线利润率) − C)，是已计入全部成本之后的新增空间，不是可再次花掉的总预算 |

表内利润和获客空间均为单件值，整单展示乘以 Q 并明确标注；不得混用单件成本与整单收入。

P 在纯内部测算时明确标为目标售价；正式报价分析必须使用人工选择的实际客户报价单价，
不能用目标售价的利润替代较低成交价的利润。报价币种与核算币种不同时，用冻结的显式
报价换算关系还原其核算价值；该换算是已声明方案的代数关系，不是临时查询新的反向汇率。
审批包同时显示客户币种金额、核算币种成本、使用的汇率和总量口径。

所有 Money、比例和汇率仅接收有限 Decimal，HTTP 用十进制字符串。拒绝 float/bool、负成本、
非正数量、零或负正式售价、非法利润率、缺币种、缺汇率、无确认成本和溢出；拒绝超出存储精度
而会被数据库静默舍入的输入。不得静默截断、以零成本兜底或用模型填值。
合法的单项零费用可保留其人工确认依据；完整成本为零时可显示原成本事实，但停止自动定价及
依赖售价作分母的利润率计算，返回明确原因，不能产生除零或“无限利润”。

中间计算使用固定、版本化 Decimal 上下文，不提前量化。正式展示按已确认精度舍入；客户可见
单价乘数量得到行额，行额汇总得到总额，不能各处各算一遍。舍入后重新计算实际可见价格的利润，
如行额按货币精度舍入，以最终客户总额除以 Q 得到有效单位收入参与利润判断，不忽略舍入差额。
低于底线仍须阻断或独立批准例外。财务空间为负时仍显示负利润和低于底线原因，不因上限取零而掩盖亏损。

`inputs_hash` 覆盖金额/币种/数量/单位、成本及价格依据、全部汇率、政策版本、成本归类、
场景清单、报价实际价格与精度、算法版本；Decimal 规范化为无二义的字符串，重复项不丢弃。
计算时间由调用者显式注入，不参与数值输入哈希；相同输入和算法必须重现相同数字及哈希。
现有 `compute_breakdown` 的输入不足以承载这些语义，需以显式 typed 参数扩展并留契约 ADR，
不能在函数内部读取数据库、当前汇率、环境默认规则或系统时钟。

## 六、锁定、报价版本与审批

### 6.1 报价依据冻结

创建报价时服务端读取该租户真实机会、需求/规格版本、成本和价格依据，不接受客户端声称已锁定。
先验证权限、数量/规格/目的地匹配、成本完整性、政策和有效期，再锁行生成不可变报价依据快照。
快照包含成本版本、计算结果/hash、价格依据、汇率、规则、确认人和客户条款。检查与锁定之间
若成本、需求版本或归属已改变则返回冲突；禁止“先读后写”把过时的检查结果锁成有效依据。

一个带持久幂等键的创建操作绑定这些依据和新报价版本。采用可恢复的分步提交：先幂等锁定成本并
写操作关联，再在 quotations 事务内建报价和版本记录。中途崩溃同键恢复，不能解锁成本或换键复制报价。
前置验证失败不锁成本；已锁而尚未建报价的状态可见为待恢复，不冒充成功。跨域各用自身 UoW，
不由 costing 直接操作报价表。

### 6.2 报价生命周期

沿用 `draft → pending_approval → approved → sent → accepted/rejected/expired` 和 superseded。
本批主流程止于 approved 与文件交付，不自动进入 sent。提供可信发送回执的接入契约和受控测试，
但没有实际发送记录时不能标 sent；下载 PDF 不是发送回执。

报价内容创建后不可原位改写。人工“修订”显式创建新版本，并在同一报价事务中将旧活跃版本
superseded；界面先提示旧版本将停止使用。旧的 pending 审批即使稍后批准也不能使旧报价恢复活跃。
并发修订只允许一个成功，冲突方重新读取，不自动创建另一个版本。

现有状态表未允许 draft/pending 的修订和未发送报价的过期，需显式补全这些转换并测试：
draft/pending/approved 可以 superseded 或 expired，但仍不能越过审批到 sent；审批拒绝转 rejected。
accepted/rejected 不允许重写，保留历史。过期不能靠“重新提交”延长，必须创建新版本并重新核验依据。
系统标 superseded 只停止系统继续使用，不声称已撤销客户手中旧文件构成的承诺；通知客户由人工处理。

### 6.3 审批与例外

审批包展示报价全文、真实采用的售价、成本摘要、全成本利润率/底线、遗漏或参考价风险、有效期、
价格与汇率依据、历史版本差异及全部商业条款。拟包含的折扣、交期、付款等承诺逐项列明审批类型；
普通报价批准不能隐含批准包外承诺。缺少适用审批事实的承诺禁止进入正式客户文件。

低于底线使用既有 `MARGIN_FLOOR_OVERRIDE`，针对同一报价内容 hash 独立批准；它不代替正式报价审批，
也不允许参考价伪装 QUOTED。报价仍须常规审批。无需例外时不多建例外包，不建设多级审批链。

审批人不得等于起草人或机会负责人，且需当前在职、满足既有 ABAC；界面权限仅作提示，服务端再次核验。
自批限制在本批不增加老板豁免。审批引用绑定 tenant、对象 ID、版本和内容 hash，不能重用另一份报价的批准。

`ApprovalDecided` 是触发，不是可单独信任的授权证明；handler 读取持久审批事实，校验类型、对象、
hash、批准人、当前归属和有效期，再将报价状态与 `QuoteApproved` outbox 原子提交。
重复事件、重复点击和重启只应用一次；拒绝、过期、归属变化或内容不匹配不能自动补批。
先完成报价侧幂等效果，再按既有契约标记 approval applied；失败留可追踪状态，不盲目自动重试到成功。

客户报价有效期不得晚于本方案任一适用价格依据有效期。正式文件生成/下载前重新检查报价仍活跃、
未过期、审批事实与依据仍适用；不因曾收到 `QuoteApproved` 就永久放行。事件本身不触发邮件工具。

## 七、API、界面与客户文件

扩展现有 `/costing-quotes` 页面与对应 router，不新建另一套成本系统：

- 成本版本列表、确认来源和适用清单、老板核算/利润政策配置、测算结果及逐项“为什么”。
- 新建报价、内部预览、提交审批、修订、历史版本对比和受控客户文件下载。
- 审批中心接收结构化报价包，支持原文证据展开；Run 展示等待审批、阻断和应用结果。

现有成本读取/创建角色不自动扩展；老板才可确认政策。报价创建只向已有成本操作角色开放，
审批权仍由 approvals 决定。业务人员的客户文件读取须同时满足机会访问权，不能借文件端点取得内部成本。
请求不传信任字段；前端金额用字符串呈现，禁止 JavaScript Number 重算交易金额。

新业务 DTO 定义在域 schemas 并生成 OpenAPI 类型。内部 DTO 可以带成本、供应商、底线、利润和
原文引用；客户 DTO 用字段白名单，只含本公司已确认抬头、客户、报价编号/版本、产品规格、数量、
客户价、币种、有效期和已批准条款。成本、利润、供应商采购价、内部备注及原始资料引用不得进入客户 DTO。

PDF 由确定性模板渲染，不由模型生成金额。草稿仅内部鉴权预览且清楚标记“未批准”；正式文件仅
批准且当前有效时生成。文件存储 tenant、quote/version、客户内容 hash、模板版本、artifact hash 和生成记录，
同一键重试复用已有文件。模板升级不覆盖旧文件；经审批内容 hash 未变且模板属于安全呈现变更才可重新渲染。

渲染器只接收客户 DTO，不加载外部图片/URL、脚本、字体或附件；文本需转义，限制长度、大小与页数。
内部证据和凭证不可进入 PDF 元数据、文件名、日志或事件。下载经过实时鉴权，不创建永久公开对象链接；
被取代/过期的文件只供有历史审阅权限的内部用户查看，不能作为当前有效报价重新导出。
此前已被人下载的文件无法远程撤回，界面须说明此限制。

本批不加自动发送按钮或任意附件发送后门。后续接入实际发送，仍需真实可达性、抑制、身份信誉、
政策、审批和持久幂等门禁；不是本设计已完成发送接线的承诺。

## 八、数据库、故障与兼容

新增或扩展：价格依据及字段确认、场景清单/核算政策版本、规则来源、计算/锁定快照、报价及行、
版本/状态审计、审批关联、文件关联、跨步操作幂等记录。复用既有成本、员工、机会、审批、Run、
outbox 和 artifact 表，不建立平行身份/审批存储。

所有记录有 tenant_id；外键采用 tenant+ID；仓储查询强制租户过滤。数据库约束保证：同机会版本唯一、
活跃报价唯一、同幂等键同载荷、锁定成本不可修改、报价内容和证据快照不可变。状态变化写审计记录，
不能通过更新删除历史。索引按租户+机会/状态/到期时间服务实际查询。

新增迁移使用下一可用 revision，不修改已合并迁移。验证 upgrade → downgrade → upgrade、ORM 一致性、
旧数据阅读和新检查；禁止启动时自动迁移或对生产库试跑。

结构化失败至少区分：政策未确认、成本未确认/漏项、重复成本、证据不可访问、价格非实报、
规格/数量不匹配、价格依据过期、汇率缺失、利润低于底线、审批缺失/自批/失效、版本冲突、
锁定待恢复、文件生成失败/状态未知和权限拒绝。错误不输出原始 SQL、DSN、凭证或资料内容。
文件失败不抹掉已批准事实，不把未知存储结果当作未生成后自动换键；确定性恢复使用相同内容与幂等键。

保留旧成本 API/readiness、已有研究 v1/v2 与 Campaign 工作流。新增报价流程使用版本化定义，
只在实际依赖就绪时装配；依赖缺失返回明确不可用，不注册空壳“可用”工具。实际 API 与 scheduler
装配必须在集成测试中覆盖。研究 `research_only` 不因报价能力上线而新增任何报价调用。

## 九、实施切片与验收

下列是顺序与验收边界，不是逐文件实施计划；书面设计批准后再用 writing-plans 展开。

1. 契约与计算：补齐核算/利润政策和来源、定义 Decimal 公式/精度/hash；先失败测试再实现。
2. 证据与锁定：价格依据、完整性检查、不可变成本快照、并发/幂等/重启恢复及迁移。
3. 报价与审批：报价持久化、修订/过期、审批绑定、独立审批、应用和真实进程装配。
4. 界面与客户文件：生成类型、内部/客户 DTO 隔离、PDF、历史和结构化阻断状态。
5. 整体验收：受控资料贯穿录入→计算→报价→审批→文件，独立审查、全量回归及浏览器验收。

必须覆盖的断言：

- Decimal 输入、单件/整单、22 类成本归属、缺项、重复来源、外币方向、舍入后跌破底线，
  以及目标售价与人工实际报价的利润区别；同输入数字/hash 可复现。
- 未确认模型金额不计入，规则/精度未配置不定价；网页参考价和失效/跨租户证据不能进正式文件。
- 数量档/MOQ/规格/目的地变化重新核验；Actual 费用不伪装实际收入或成交。
- 锁定与追加并发、两个修订并发、同键不同请求、成本锁后崩溃、报价提交后 outbox 重投与审批应用重启。
- 自批、离职/越权审批、旧版本/旧内容审批、已过期审批、旧 pending 审批晚到，均不能生成有效正式文件。
- 低于底线需要对应例外与正式批准；折扣/交期/付款等未获明确审批的承诺不得随报价混入。
- 修改规则或供应商资料不会覆盖历史；历史审批不能批准新内容；过期和 superseded 文件不当作当前报价。
- 客户 DTO、PDF 正文/元数据/附件中均无内部成本、利润、底线、供应商采购价或敏感原文；外部资源加载为零。
- 老成本 API、Campaign 和免费研究回归；本批受控主流程的真实搜索/联系人/邮件调用数为零。

执行结构检查、相关后端测试、隔离数据库迁移、后端全量与串行 E2E、前端测试、类型检查、
构建、OpenAPI 漂移检查和浏览器验收；PDF 做内容提取检查与渲染视觉检查。
每一项以真实命令和证据登记，不把设计清单当作通过结论。

验收报告分栏记录受控流程、真实资料核验、真实发送/客户反馈、未运行项。没有用户提供真实
资料或配置时，相关项为 `not_run`；工程闭环通过不等于 Phase 2 全部完成或获得真实利润。

## 十、设计自检与后续状态

- 范围：只交付人工证据驱动的成本/报价/审批/文件，不暗中启动自动寻源或发信。
- 契约：缺失的价格依据、核算口径和锁定可信来源有明确归属；不靠客户端布尔值授权。
- 安全：未降低九条硬边界；QUOTED 行约束比根规则更严格，保留原成本风险接受阅读但不扩大使用范围。
- 兼容：历史记录不补造证据，历史 workflow 不改解释；新报价状态转换在 ADR/测试中明示。
- 商业决策：没有写入利润率、折扣授权、汇率、成本数值或生产预算默认值；数学空间不构成支出或承诺许可。
- 完成度：本文已通过用户书面复核；实现、测试、真实业务验证分别记录，当前均不由本设计声称完成。
