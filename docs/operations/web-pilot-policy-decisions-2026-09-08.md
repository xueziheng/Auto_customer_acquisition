## 用户已明确决定

| 项目 | 规则 | 对话依据 |
| --- | --- | --- |
| 负责人 | 分配后由员工持续负责；不因等待或超时自动转走 | “就一直让员工负责就行，员工不负责再交给你” |
| 退回触发 | 只有员工主动退回，才交回系统 Agent；不能以不活跃推断员工拒绝负责 | “员工主动退回” |
| 币种 | 内测业务币种采用美元 `USD` | “美元” |
| 金额分档 | 暂不设置大小单分档及分档阈值 | “多大的单子就暂时不弄了” |
| 提醒间隔 | 尚未处理的商机每隔两小时提醒，即 `7200` 秒 | “每隔两个小时吧” |
| 停止提醒 | 员工点击接受接管后停止提醒，仍由该员工持续负责 | “员工点击‘接受接管’后就停止提醒” |

这些决定不代表新增真实客户发送权限，也不改变现有逐次人工审批约束。USD 不代表允许自动换算已有其他币种数据。
暂不做金额分档，不等于取消既有报价、利润、市场准入或最低订单额的独立硬门槛。

## 为避免歧义而单独记录的解释

- 上一轮同时询问“只给员工”或“同步给老板”，用户回答“可以的”，没有明确选定受众。
  控制者本轮已说明：先按只提醒负责员工记录，暂不抄送经理或老板。这是可调整的实现假设，
  不能伪装成用户明确选择了某个选项；此时尚未向任何人发送通知。
- 当前本机 pilot 的可用渠道为站内通知。本轮“两小时”不是创建 Codex 定时任务、邮件或桌面通知的授权。
- 用户未指定工作时间日历。连续经过两小时与只计算工作时间不同，落地时必须明确采用哪一种。
- 用户已进一步明确：未处理在本次提醒中指尚未接受接管。接受后停止催接单，员工仍持续负责；不新增接单后持续催办。
- 两小时提醒间隔不是两小时 SLA 违约判定，更不是自动换人的时间。用户没有提供积压告警阈值，不能填测试数字。
- 用户未配置七档证据到高/中/低展示桶的映射。该映射与订单金额分档是不同配置，不能由暂停金额分档推定。

## 建议的落地顺序

1. 配置表达：明确金额分档关闭模式及只提醒负责人模式，保留旧显式策略兼容；未提供的业务规则仍如实显示未配置。
2. 提醒执行：复用持久化 scheduler 与站内通知出口；每次读当前状态和负责人，按轮次去重，重启不会对同一轮重复发通知。
3. 主动退回：要求真实当前员工操作，保存退回人、时间、原因和必要上下文；与接管/提醒并发时保持原子性，成功后停止该员工的待接管提醒。
4. Agent 接续：与退回记录分开表示任务是否真正入队、是否有可用执行器；未启用时明确待处理或不可用，不能假成功。
5. Web 验收：检验重复请求、跨租户/错负责人拒绝、两小时边界、接单/退回停止提醒、恢复后不重复通知，以及关闭金额分档后的真实启动行为。

提醒定义必须与用户确认的规则一致，再进入实现和正式配置。配置文件、账号与任何凭证仍由既有私有 profile/TTY 路径管理；此记录不含密码、Cookie 或外部服务凭证。
