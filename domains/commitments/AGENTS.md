# domains/commitments/ —— 承诺域（浅，模型写全）

## 职责

**Commitment Ledger（承诺账本）**：员工和客户说出的承诺，单独管理、到期提醒、逾期升级。

```text
员工说 "I will send the quotation tomorrow."
    → 员工承诺：发送更新报价，明天到期
客户说 "We will confirm the quantity on Friday."
    → 客户承诺：确认最终数量，周五到期，状态 waiting_customer
```

## 为什么承诺值得单独一个域

散落在聊天记录里的承诺等于没有承诺——没人记得、没人跟、到期没动静。而贸易成单的节奏恰恰由承诺链驱动：我发报价 → 你确认数量 → 我确认交期。承诺断在哪，单子就停在哪。账本让「谁欠谁什么、什么时候到期」变成可查询、可提醒、可升级的数据。

## 相对时间必须在提取时解析为绝对时间

**存 "tomorrow" 一周后毫无意义。** 提取时就要用消息时间戳 + 客户时区解析成绝对时间：

```text
消息发于 2026-08-07 15:00 (客户在加州)
"by Friday" → 2026-08-08 23:59 America/Los_Angeles
```

解析不确定时（"soon"、"later this month"）宁可标记 `due_at_uncertain` 让员工确认，不要猜一个精确时间——错误的精确比诚实的模糊更有害（提醒会在错误的日子触发）。

## 升级路径

```text
员工承诺逾期  → 提醒本人 → 再逾期升级到经理
客户承诺到期  → 提醒负责员工跟进（客户不会自己想起来）
```

## 提取与确认

承诺由 `agent_runtime/team_operations` 从会话和上传里提取，但**提取结果要经员工确认**（同数据平面的修改留痕规则）——模型把客套话当承诺、把承诺当客套话都会发生。未确认的承诺不进提醒管道。

## 依赖白名单

```text
允许   shared.*        禁止   其他 domains/*、外部 SDK
```

## 事件

发布：`CommitmentCreated`、`CommitmentOverdue`
订阅：无（提取由工作流驱动写入）

## Phase 1 范围

账本模型、到期扫描、升级规则、确认流程。不做：承诺自动完成检测（判断「报价发了没」需要跨域推理，Phase 2）。
